mizrab's tests follow the convention of Salam's own test corpus and of basalam: a test is an ordinary Salam program, and its stdout is the expected result. `make test` builds the binary, then runs `sh tests/run.sh`.

## Convention

- `tests/<name>_test.salam` is a normal program. It asserts with `std/testing` and ends with `ret testing.Summary()`, whose return value is the exit code.
- `tests/<name>_test.out` is the exact expected stdout: the `--` separator line and the `tests: N passed, M failed` summary. For `tests/cli_test.out` that is `tests: 2 passed, 0 failed`.

A test passes when it builds, exits 0, and its stdout matches the golden byte for byte.

## What the harness does

For each test program, `tests/run.sh`:

1. builds `tests/<name>_test.salam` into `build/tests/<name>` with `--backend=llvm --log-level=warn`, from inside `tests/`: the compiler checks a `link static` path against the source file's directory but hands it to the linker from the working directory, so the two agree only there;
2. runs it with an empty stdin, so a test that reads the terminal cannot pick up input;
3. bounds the run with a 30-second watchdog, so a hung test fails instead of stalling the suite; `TEST_TIMEOUT` in seconds overrides the bound;
4. fails on a non-zero exit code, a timeout, or a `diff -u` mismatch against the golden.

The harness needs `build/mizrab` and stops if it is missing, which is why `make test` builds first. Calling the harness directly needs a prior `make build`.

Before the first binary invocation, `run.sh` points `HOME` and the four `XDG_*` variables at directories under `build/tests/`, so a test that needs a config file writes one there and never in the real home.

| `walk_test` | the library walk: the fixtures in sorted order, with the symlink and the non-audio file left out; dot-names, letter case, a symlinked directory and the 32-level depth limit on a tree built at run time |

| `rescan_test` | `ScanPlan` and `MergeScan` on hand-built data, then `Scan` on real files: what is re-read, what is kept, what drops out |

| `keymap_test` | the keymap on a headless screen: the preset directions and `/`, `Tab` and the arrows, and the four keys mizrab binds itself, with no terminal |
| `shell_test` | the [app shell](/app-shell) on a headless screen: the root tree and the panel bounds at 80 × 24 and at 40 × 12, the four focus stops and the ring order, the header never being a stop, the hint ladder and the degrade threshold |
| `loop_test` | the event loop: the four keys becoming commands, a tick calling the tick callback and reporting nothing, and `q` stopping the loop before any verb is applied |
| `terminal_test` | the terminal guard, headless: the restore bytes and their order, the absence of a mouse sequence, the flag file replayed and removed, `Begin` and `End`, and `IsTTY` false under the harness |
| `instance_test` | the single-instance lock: the path rule, the exclusive create, the refusal line, and reclaiming a lock whose pid is dead or whose contents are not a number |
| `unicode_test` | the measured Unicode record: byte, codepoint, grapheme and `term.Width` numbers for a fixed corpus, and how titles sort |

`decode_test` and `engine_test` link `build/miniaudio.o` and `build/ma_shim.o`, which `make build` produces, and read the audio files in `tests/fixtures/`. The library tests link `build/library_shim.o`. The engine test needs no sound card and no ALSA configuration, so it runs on both CI legs. `tests/soak.sh` is not a test and `run.sh` never discovers it; `make soak` runs it (see [make targets](/make-targets)).

`tests/gap.sh` is not a test either, and `run.sh` does not discover it. It is run by hand, after `make build`, to record the inter-track gap on the real audio backend; see [the playback controller](/playback-controller#the-inter-track-gap).

## The binary smoke checks

After the test programs, thirteen checks run against the real binary rather than a test program. They run on every invocation, including a single named test:

- `--version` exits 0 and prints the pinned version;
- `--help` exits 0 and prints the usage line;
- an unknown flag is a usage error, exit 2;
- `--scan` writes an index and prints the summary line;
- a second `--scan` of the same root reads nothing and writes the same bytes;
- the index carries the schema number;
- a missing root exits 1 and a missing root argument exits 2;
- a config file with a bad line exits 2 and the message names the line;
- a config file in `XDG_CONFIG_HOME` supplies the roots to a `--scan` with no positional root;
- a positional root and `--index` override the config's `roots` and `index`, so only the flag's index is written;
- an explicitly named config that does not exist exits 2 with `cannot read`;
- `--version --config` still prints the version and exits 0, so the file is not read on the fast path.

They count towards the failure total only; the `N passed, M failed` summary counts test programs.

## Run one test

```sh
make build
sh tests/run.sh cli_test
```

With no names, the harness runs every `tests/*_test.salam`. A name narrows the golden checks; the thirteen smoke checks still run.

## Add a test

1. Write `tests/<something>_test.salam`, using `std/testing` assertions and ending with `ret testing.Summary()`.
2. Run it and read the output:
   ```sh
   sh tests/run.sh <something>_test
   ```
3. When the output is what you expect, save it verbatim as `tests/<something>_test.out`.
4. Run `make test` to confirm the whole suite and the smoke checks pass.

Goldens are byte-exact and there is no update flag: the `.out` file is edited by hand. `make test` and the harness only read `tests/`; neither rewrites a golden.
