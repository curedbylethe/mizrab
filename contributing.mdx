mizrab is a Salam program, so its style follows the compiler's formatter rather than taste. This page covers the code style, the commit convention, the five pinned versions and how to report a defect upstream. For the commands themselves see [make targets](/make-targets), for the harness see [tests](/tests) and for the tree see [repository layout](/repository-layout).

## Code style

- `salam format` is the authority. Run `make fmt` before committing; `make fmt-check` is the gate that rejects unformatted files.
- Indent with 4 spaces. `.editorconfig` matches the formatter.
- Every file starts with the GPL-3.0-or-later licence header comment. `make header-check` rejects a source without one and names the file.
- Declaration order is imports, then `include`s, then declarations. The formatter enforces this order (`--fix-order` is on by default) and the compiler rejects the wrong order outright.
- Every `pub` declaration carries an `@en "Name"` annotation followed by a `///` doc comment, which is basalam's convention. The doc comment comes after the annotation so `salam doc` picks it up.
- Write the language, not a binding: use `std/term` for escape sequences.

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, with a scope when it helps.

```text
feat(commands): add the version command
chore(deps): bump Salam to 0.5.7
```

- Imperative mood in the subject.
- One coherent change per commit; no `wip` or `fixes` commits.
- The tree is green after every commit: `make check`.

### Bumping a pin

1. **Salam compiler.** Edit `.salam-version` and the `salam` floor in `salam.toml` in the same commit. `.salam-version` was the only place the version appeared, and it no longer is: `salam.toml`'s `salam = ">=X.Y.Z"` floor names a compiler version too, and moving one without the other leaves the tree half-bumped. The `Makefile` reads `.salam-version`, and CI asserts that `salam version` matches it.
2. **basalam.** Take the release from the registry, which writes the manifest and the lock:
   ```sh
   salam add github.com/curedbylethe/basalam@vX.Y.Z
   ```
   Commit `salam.toml` and `salam.lock` together, then record the tag, the commit it points at and the sha256 in the table above. Name the tag explicitly rather than running a bare `salam update`: that moves within the same major version, and before 1.0 that covers every `0.y` minor, which mizrab treats as breaking.
3. **miniaudio.** Replace `audio/miniaudio.h` with the file from the chosen release, then update the version, the release link and the `.h` sha256 in the table above. Do not edit `audio/miniaudio.h`. Leave `audio/miniaudio.c` alone: it is the local implementation unit, and its `#include "stb_vorbis.c"` is the only thing that compiles the Vorbis decoder in. If you do change it, re-record its sha256 in the table.
4. **stb_vorbis.** Download `stb_vorbis.c` from `nothings/stb` at the chosen commit with `curl -fsS https://raw.githubusercontent.com/nothings/stb/<commit>/stb_vorbis.c -o audio/stb_vorbis.c`, then update the commit, the link and the sha256 in the table above. Upstream ships no separate header: `audio/miniaudio.c` includes the file whole, before `miniaudio.h`. Do not edit the vendored source.
5. **Mintlify CLI.** Edit `.mint-version`. That file is the only place the version appears: the `Makefile` and the CI `docs` job read it, and the README names the file rather than repeating the value.
6. **Salam setup action.** Replace the commit in the `Setup Salam` step's `uses:` with a commit from [`SalamLang/Salam`](https://github.com/SalamLang/Salam), then update the date and the value in the table above. Never point that step back at `@main`: the release the action downloads is already pinned by `.salam-version`, so a moving action ref can only change the install path, cache key or asset naming under you.

Verify the whole tree on the new pin before committing:

```sh
make clean && make check
```

Commit as `chore(deps): bump Salam to X`, `chore(deps): bump basalam to vX.Y.Z` or `chore(deps): bump Mintlify CLI to X`, with the new value recorded in the table in the same commit. If a bump breaks the build, that is a finding to report upstream, not a reason to loosen the pin or fall back to `latest`.

## Upstream findings

Any limitation in the Salam compiler or standard library, or in basalam, is reported upstream as it is found. Do not work around it silently. A report needs four fields:

1. **`salam version`**: the full output, not just the number.
2. **OS and terminal**: for example "macOS 15.6, arm64, Ghostty".
3. **Minimal reproduction**: the smallest program, or the exact command, that shows the problem.
4. **Expected vs actual**: what should happen, what happens instead, including the exit code and the relevant stdout/stderr, plus the workaround used.

File it at [Salam issues](https://github.com/SalamLang/Salam/issues) or [basalam issues](https://github.com/curedbylethe/basalam/issues), then link it back from `FINDINGS.md`, the log of local findings and their upstream links.
